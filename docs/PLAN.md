## 0. 一句话定位

**本地优先、可独立运行的求职投递平台**：粘贴即可导入公司与内推信息，自动识别公司类型并生成"待补充信息卡"，三遍质检保证填写准确，登录与最终提交始终由用户本人完成。

## 1. 目标用户与场景

- 任何求职者（不是单人专用）：导入自己的简历、个人资料、公司清单后即可使用。
- 输入五花八门：微信群消息、文档表格、纯链接列表、单个链接+码；**有的用户没有内推信息** → 流程自适应，不阻塞。
- 本地运行，数据不出机器；模型可选 BYOK；不依赖任何 Agent harness。

## 2. 硬边界（不变）

1. 不代登录、不代验证码、不代最终提交；"继续投递"≠授权提交。
2. 填写只用本人确认文本（原文复制，不改写、不截断）。
3. 未知不编造；冲突挂起待核；不确定不默认"无/否"。
4. 已投不撤回、不删除、不重投；页面已填≠已保存≠已提交≠官网核验。
5. 仓库只有代码与虚构测试数据；真实简历/资料/密钥不进 Git。

## 4. 粘贴导入设计（核心能力）

### 4.1 处理链

```text
粘贴杂乱文本
→ 拆分出 N 家公司
→ 每家识别：公司名 / 校招链接 / 内推链接 / 内推码 / 渠道提示 / 批次 / 截止日期
→ 自动判定公司类型（置信度 + 依据）
→ 选中对应类型的信息卡模板
→ 与资料库比对 → 只列"待补充"字段
→ 用户确认/修改 → 保存
```

**平台 ≠ 类型**：Moka / 飞书系 / 北森（zhiye）/ hotjob / 自建官网 = 申报系统（决定填写方式）；银行 / 车企 / 制造 / 互联网 / 快消 = 类型（决定问什么、核查什么）。两者分开存储。

### 4.2 解析字段清单

| 字段 | 规则示例 |
|---|---|
| 公司名 | 【】内文字、编号行标题、行首实体 |
| 链接 | URL 正则；按域名归平台（mokahr.com、jobs.feishu.cn、*.zhiye.com、hotjob.cn、短链 dwz.cn/wxmpurl.cn 等） |
| 内推码 | `recommendCode=` 参数、`内推码[:：]` 后缀、括号内孤立字母数字串 |
| 渠道提示 | 大使推荐 / 校园大使 / 员工内推 / 内部推荐 / 链接自带 / "点击链接投递即可" |
| 批次/截止 | 2026秋招、2027届、X月X日截止 等模式 |
| 原文 | 该条目原文片段（rawSource）完整保留 |

### 4.3 公司类型识别（多信号打分）

| 类型 | 识别信号 | 信息卡重点 |
|---|---|---|
| 银行/金融 | 名称含银行/证券/保险/基金；域名含 bank | 身高体重、家庭社会关系、奖惩、征信声明、意向分行 |
| 车企/智驾/机器人 | 汽车/智驾/自动驾驶/机器人/激光雷达；nio、geely 等关键词 | 驾照、出差驻场、海外派遣、意向城市数 |
| 制造/国企/央企 | 集团/重工/电子/钢铁/能源；"中国/中电/中核"前缀 | 政治面貌、户籍档案、政审体检类 |
| 互联网/科技 | 科技/网络/信息/软件/游戏；飞书系链接常见 | GitHub/作品集、技术栈、游戏经历（必须问） |
| 快消/运营/零售 | 食品/饮料/服饰/消费；已知名单 | 实习社团、英语、海外/签证、轮班 |
| 其他/自定义 | 无匹配 → 通用卡，用户选择或新建类型 | 通用字段集 |

打分：精确名单 +3；名称关键词 +2；域名关键词 +1；渠道/公告提示 +1。
- ≥3 → 高置信默认选中；1–2 → 显示"识别为 X（置信度）"+ 备选；0 → 不确定，默认通用卡。
- 识别依据随行展示（如"匹配到：银行（名称 +2、域名 +1）"）。
- **用户纠正本地学习**：改一次 → 写入别名表（如"某某机器人 → 车企/智驾/机器人"），下次秒判；仅存本机。
- 一司多类型 → 主/备选并列，等用户点，不硬选。

### 4.4 信息卡生成（集合差）

```text
信息卡 = 类型模板字段 ∪ 公司手动补充字段 − 资料库已有 − 本表单不适用
```

卡片样式（示例，内容为虚构演示）：

```text
【某公司】 车企/智驾 · Moka · 码 XXXXX（链接自带，待核绑定）
▶ 需你回答（3 项）：驾照？接受海外派遣？期望年薪？
▶ 将直接复用（12 项）：个人/教育/实习×4/项目×4/研究/社团/奖项/语言/技能/自评…
▶ 适用范围：仅该公司/本批次
[确认类型]  [去补充]  [以后再说]
```

### 4.5 异常与缺失处理

| 情况 | 处理 |
|---|---|
| 无内推码 | 标 `no-referral`，跳过码字段，不编造 |
| 码冲突（两处值不同） | 双候选 + `conflict` 状态，挂起待核，不自动选 |
| 只有公司名 | 标"待补充链接"，不阻塞其他公司 |
| 同公司多链接 | links[] 带 kind（apply/referral/career-site）；归一 URL 去重 |
| 重复粘贴同一公司 | 按 公司名+链接 合并，保留原有卡与别名 |
| 表格粘贴（腾讯文档等） | 识别表头/制表符 → 列映射 |
| 平台多样 | 平台字段独立于类型；同一类型可跨平台 |

### 4.6 速度设计（"反应非常迅速"）

1. **同步本地优先**：解析+分类全为纯函数、无网络；粘贴即渲染（设计目标：50 条 < 100ms）。
2. **LLM 仅兜底**：仅对"不确定"条目、且用户主动点"帮我想"才异步调用；永不阻塞首屏。
3. **别名缓存**：确认过的公司→类型映射本地缓存，二次粘贴秒判。
4. **分块渲染**：大清单按行增量渲染，已解析的行先可交互。
5. **落盘节流**：编辑时内存更新，防抖写入存储。

### 4.7 准确性设计（"确保信息准确"）

1. 类型/码/链接**只是候选项**，全部经用户评审确认后才入库。
2. 展示识别依据与置信度，可审计。
3. 用户纠正持久学习；同一错误不重复出现。
4. 冲突与低置信不隐藏，显式标黄。
5. 所有条目保留 rawSource 与 provenance，可回溯原文。

## 5. 字段分级（通用机制）

| 级别 | 定义 | 通用示例 |
|---|---|---|
| A 可直接复用 | 资料库已确认，不再逐公司问 | 姓名、教育、实习、项目、语言、技能等 |
| B 每公司询问 | 逐公司确认，不跨公司沿用 | 内推码/渠道、亲属任职、证书编号、调剂/派遣/薪资/到岗、历史声明、证明人、特殊资格 |
| C 来源核实 | 官网/材料核对，不靠询问臆答 | 毕业窗口、官网历史记录与额度、码绑定状态、附件版本、按钮语义 |

回写机制：询问卡（一次问完）→ 本人回答 → **公司确认卡**（字段/回答/日期/来源/适用范围）→ 同步资料库。

## 6. 公司类型模板维护规则

1. 新字段 → 判级别（A/B/C）→ 归入对应类型模板 → 记入当轮询问卡。
2. 同类型第二次出现且有确认卡 → 直接复用，不重复询问。
3. 公司特定回答标"仅该公司"；跨公司复用须本人确认。
4. 模板用户可编辑（增删字段、新建自定义类型）；变更记录在运行日志。

## 7. 三遍质检流程

**通用规则**：外置记忆（文件为准）；长文分段填入+即时读回；`fill→blur→读回`，diff 只允许换行归一化；每步留痕。

### 遍1 · AI 填写（便宜模型 + 脚本）
字段计划 → 附件一次性上传（解析风险前置处理）→ 短字段批量填 → 长文本分段填+读回 → 日期控件真实交互读回 → 脚本必填/格式/长度校验 → 产出作业单（已填/未决）。
禁止：代登录、点提交语义按钮、猜填声明、重解析覆盖手改。

### 遍2 · 独立复核 + 补充（另一模型/另一次运行）
独立上下文只读"读回快照+资料库+确认卡+JD" → 逐栏对照（数量/日期/城市/志愿顺序）→ 长文 diff → 幻觉扫描（不存在技术、已发表说法、游戏经历、独立开发角色）→ 附件声明复查 → 能机械补的补，其余升级询问卡 → 产出复核报告（必改/建议/存疑）。

### 遍3 · 用户终审提交
送审单（公司/岗位顺序/资格/额度/资料版本/保存状态/待补/风险）→ 本人检查修改 → 本人点提交 → AI 只读核验记录 → 状态升级 → 更新台账。

### 检查点 G0–G4

| 检查点 | 时机 | 通过标准 | 不通过 |
|---|---|---|---|
| G0 资料与附件 | 打开表单前 | 版本正确、口径最新 | 修正后再开始 |
| G1 资格/历史/额度 | 登录后填表前 | 历史/窗口/额度/内推已核 | 转待核或跳过 |
| G2 字段计划 | 填写前 | 每字段有来源；B 类已问 | 先问后填 |
| G3 填写与保存后 | 遍1/2 后 | 读回 diff 通过；保存证据如实 | 修复重检 |
| G4 送审与提交后 | 提交前后 | 送审单完整；官网已核 | 降级待核验 |

## 8. Agent 分工与外置记忆

| 角色 | 负责 | 不负责 |
|---|---|---|
| 强模型 | 匹配排序、冲突判断、遍2 复核、异常解释 | 不逐字段调用；不改写确认文案 |
| 便宜模型 | 字段映射、JD 提取、遍1 批量填写、询问卡生成 | 不做终审决策、不代提交 |
| 脚本 | 必填扫描、格式/长度/数字校验、读回 diff、去重与额度查询、日志生成 | 不做语义判断 |
| 本人 | 登录/验证码、B 类回答、终审、提交 | — |

- 并行：只读检索可 subagent 并行；**写操作串行**，同一表单单写入者。
- 防幻觉四件套：外置记忆 → 分段+即时读回 → 交叉模型复核 → 脚本硬校验。

## 9. 状态追踪与去重

**状态机**：待核查 → 等待本人登录 → 核查中 → 填写中 → 待本人审核提交 → 本人报告已提交 → 官网核验成功；旁路：待补资料/规则待核/待修复/跳过/额度已满。

**去重主键**：申请人 + 公司主体 + 招聘批次 + 官方岗位ID；有申请编号优先绑定。不同链接进同一岗位=一次申请；"链接带码"≠已绑定；内推码≠岗位ID。

**额度组**（可选功能）：同一集团多业务线共享名额时单独建模（按用户实际情况填写）；本地草稿只算"计划占用"。

**证据映射**：页面已填=读回快照；草稿已保存=保存提示/记录页；本人提交=本人说明；官网核验=申请记录读取。

## 13. 测试策略（MVP 阶段从简）

- **先不做大而全测试**。MVP 只保留轻量冒烟：少量断言覆盖"解析 / 判型 / 出卡"主路径，防止纯函数回归。
- 数据仍全虚构（Moka/飞书/北森/短链/emoji 列表/码冲突/无码），但样例数量精简。
- 真正的验证方式是**用户本人在真实页面上试用**：看布局、看解析与判型准确度、实际修正体验。
- 框架经确认成熟后，再逐步扩充 fixtures 与指标（解析准确率、类型接受率、出卡耗时、填写 diff 通过率），指标须实测记录，不预设数字。
