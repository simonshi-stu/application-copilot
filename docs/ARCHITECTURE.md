# 本地工作台架构与迭代边界

## 产品目标

Application Copilot 面向不同求职者，提供简历资料整理、公司清单导入、候选审核和确认原文复用。它不是特定人的投递脚本，也不是默认无人值守的自动海投系统。

当前版本为原生 JavaScript 资料工作台，已有可选 AI 接口检查，不是完整网站执行系统。2026-10-26 的目标调整为 OpenChamber 内的任务池与受控投递助手；新工作流见 [WORKFLOW.md](WORKFLOW.md)，以下现有模块不代表该目标已实现。

## 架构

```text
同一套 extension/ 页面（浏览器扩展／本地静态预览）
  ├─ 页面：导航、公司表格、当前公司详情、原文来源
  ├─ 页面事件编排：选择、编辑、确认、导入导出
  ├─ 纯函数：公司解析 → 类型建议 → 资料状态／信息卡
  └─ 本地存储边界：chrome.storage.local / localStorage

已有简历模块：DOCX提取 → 结构解析 → 本人调整 → 段落确认 → 原文复制
```

不要求框架迁移或搭建后台。若页面编排明显膨胀，可在 `extension/` 内拆分 UI 和存储模块，但不能为了分层重写现有简历模块。

## 状态与证据

- **草稿持久化**：用于防止关闭页面丢失，不构成人工确认。
- **人工确认**：仅表示本人检查过当前本地值；修改相关字段后失效。
- **外部核验**：内推绑定、资格、额度与提交记录有独立来源及时间，不能由人工确认推导。
- **复用**：必须有对应字段或段落的明确确认依据，且内容、作用范围和版本仍然适用。
- **候选**：保留原文及出处。冲突内推码不默认选第一项，也不能因编辑丢弃原候选。

旧数据导入不能信任携带的 `verified`／`confirmed` 标记。先校验、保留原数据，再按来源降级；未知版本应给提示，不能静默清空、覆盖或批量升级确认状态。

## 页面布局（已实现）

桌面：深色左侧导航（简历与段落／我的资料／公司与清单／设置）＋统计看板（全部／待核对／已确认／有问题，点击即筛选）＋紧凑公司表格＋当前公司详情；详情含流程步骤条、「下一步」引导按钮、填写计划（逐项复制）、AI 复核（可选）、发送前自检、可编辑元数据、内推候选选择、原文证据与四组信息卡。移动端（≤900px）为列表／详情单页切换，提供「返回列表」按钮。表格列：公司、行业建议、状态、下一步；支持关键词搜索与状态筛选。新手顺序为先解析简历（第一步）、确认字段（第二步）、再导入公司（第三步）。

草稿自动保存状态显示在侧栏底部（“草稿已自动保存 · 时间”），与手动「标记为已人工核对」分开；内推绑定与投递结果另有独立标记。

信息卡四组：已确认可复用、已识别待确认、待本人补充、需官网核实；“部分单位可能要求”为折叠提示，不进必填，不提前采集敏感资料。

行业、企业性质、岗位方向分别表达；未知保持未知，不因同类型迁移某公司的偏好或声明。

## Tabler 参考边界

- 参考项目：https://github.com/tabler/tabler；在线界面：https://preview.tabler.io/。
- 优先参考侧栏、紧凑表格、状态标签、详情表单的信息组织，用现有CSS实现；没有强制引依赖要求。
- 如复制实际源码或样式，固定版本、本地打包、保留版权与许可证说明，并核实所用第三方资源的许可。
- 不复制品牌、付费资源、用户样例，不引入图表、认证、计费和分析模块。
- 不使用CDN、远程字体、遥测或运行时远程脚本；现有MV3权限与CSP不放宽。

## 数据地点与发布边界

项目文件和主动生成的产物位于项目目录：私有资料与交接在 `private/`，截图及日志在 `artifacts/`，主动配置的缓存在 `.cache/`。它们不进入Git。

浏览器运行缓存仍由浏览器管理，当前没有服务自动将它们写到项目文件夹。用户可手动导出本地备份；将正式数据自动写入指定目录的本地服务留到后续独立任务。

公开内容限业务代码、通用项目介绍／架构及必要许可。私有计划、agent操作指令、个人资料、内推信息、密钥和缓存不得发布；`gitignore`不取消已跟踪文件或删除历史。

## 现有版本的边界

现有版本未内置浏览器自动化；Playwright／Chrome DevTools MCP 只有接入说明，项目 MCP 为本地无状态工具。已有 AI 复核使用本人填写的接口配置，但扩展运行、外发授权和网络限制仍须验证。新目标不迁移 React／Next.js、不建设云账号或 SaaS 后台；业务角色与开发 coder 分开，不能未经授权提取或复用编码账户和 Key。无论哪个阶段都不代登录／验证码／最终提交。

## 新目标架构（2026-10-26，设计未实现）

```text
OpenChamber 扩展：任务池 / 岗位选择与排序 / 问题弹窗 / 模型设置
  │ 官方 SDK 宿主通信，按能力授权，不暴露后台凭据
  ▼
受控执行连接层：OpenCode 插件和／或宿主管理服务（具体兼容方式待验证）
  ├─ 固定状态机与公司顺序队列：合法迁移、单公司运行、终态后自动推进
  ├─ 任务持久化：公司 → 岗位申请 → 字段计划 → 问题 → 检查点 → 投递台账
  ├─ 角色路由：检索模型 / 执行模型 / 独立 review 模型，均由本人指定
  ├─ 资料边界：确认版本、原文、作用范围、最少必要外发授权
  ├─ 工具权限：页面写锁、人工接管、提交禁令、幂等与恢复
  └─ 浏览器执行：已授权浏览器工具 + 首个平台适配器
       └─ 本人登录的官网页 → 安全填写 → 读回 → review → 本人提交
```

### 集成方式与明确限制

- 原生 OpenChamber 扩展可提供侧栏及全屏页；与 Chrome／Edge MV3 扩展、OpenCode 服务端插件是三种不同扩展机制，不能互相冒充。现有 `extension/` 不能未经适配直接当 OpenChamber 扩展安装。
- 当前扩展另提供 `contributes.attach` 的独立 dialog HUD，并通过 `contributes.actions` 在会话操作菜单中暴露“投递 HUD”：它轮询本地任务池 `/api/state` 显示进度和当前公司，使用 `host.onSession`／`host.onSessionLifecycle` 观察会话，并用 `host.prompt({ send: true })` 向当前会话发消息；独立窗口消息若带有明确 `targetSessionId`，HUD 先调用 `host.openSession()` 切换到该会话，再发送并确认消费；不调用 `startSession`。HUD 的关闭按钮只调用 `host.close()`，关闭的是 HUD dialog，不是会话。
- 另有 `scripts/standalone-hud.mjs` 与 `integrations/openchamber/standalone/`：Windows 入口启动受认证的本地服务和一个只绑定 loopback 的静态代理，再由系统 `mshta.exe` 打开真正独立的 Windows HTML 窗口。该窗口直接读取绑定项目的任务状态、发送有限的 `user.start`／`user.pause`／`user.resume`／`user.prioritizeCompany` 命令，并把消息写入项目私有的 `session-inbox.json`。OpenChamber HUD 打开时会把桥接队列逐条发送到当前会话并确认消费；独立窗口本身仍不具备 OpenChamber guest bridge，未打开 HUD 时消息只会排队。关闭窗口会停止辅助服务；这不是 `.exe` 安装包，也不是 OpenCode 原生插件。
- UI 可复用原生 JS 业务纯函数；按宿主要求打包脚本，不引入 React 迁移。新增 SDK 或构建工具、service 权限、OpenCode 插件及浏览器权限都须实施前另行说明并批准。
- OpenChamber 官方扩展面板在 sandbox 中，不能直接操纵招聘网站、访问登录 cookie、任意读文件或默认直连本地端口；通过批准的宿主能力通信。
- `host.prompt` 跟随当前会话模型；`host.generate` 只能调用宿主 Small Model。按角色固定多个模型需要另建明确授权的后端路由，不能假设宿主已有任意模型参数。OpenCode V2 的客户端／插件文档提供会话、模型与工具集成基础，但须核验实际安装版本及协议。
- 首选“不需要用户手动开 localhost”的打包安装体验，不承诺无需 OpenChamber／OpenCode 后台。必要的辅助服务由宿主管理且须批准；不开放无认证通用浏览器控制端口，不把全局 OpenCode 凭据交给 iframe。
- 内置浏览器可驱动能力以 OpenChamber desktop 文档为依据；web 面板本身不能等同于浏览器自动化。上传、强校验控件、全文读回与权限拦截需专项验证，不足时评估受控 Playwright／CDP，不默认多个驱动同时控制页面。
- 自动执行角色只获得经过校验的计划执行工具，不同时开放能绕过检查的任意点击、脚本或 shell 后门。若宿主通用浏览器工具无法在动作执行前强制拦截提交等危险操作，它只能用于受监督验证，不能据此宣称已实现安全自动填写。

### 数据与事件

- 公司任务含链接／内推候选／来源；岗位候选含官方 JD、时间、资格与匹配证据；本人选择与排序记录独立版本。
- 申请记录按申请人、公司主体、批次、官方岗位 ID 区分；志愿列表不自动拆成多次申请，推荐数量不等于额度。
- 字段计划引用已确认资料版本；问题含任务／字段 ID、类型、证据、依赖、状态和本人回答；实际页面读回和模型 review 报告独立保存。
- 首选在本项目 `private/` 下保存正式运行记录，由唯一后端写入；宿主 storage 只放小型 UI 偏好及引用，不存整份简历和读回。宿主 storage 实际在所连服务器、卸载可能清除；安装副本、凭据、浏览器缓存亦有宿主管理位置，不能声称自动全部位于本项目。
- 模型调用成功、会话变 idle、工具无报错都不等于填写、保存或提交成功。UI 从持久化任务记录恢复，并重新读取网页；事件丢失后不能只靠事件流拼出成功状态。
- 普通问题不发阻断请求；任务进度用 toast／角标，首轮填写和 review 结束后集中弹窗。安全问题立即暂停受影响步骤，未决项不能标为已完成。

实施前仍先处理当前确认失效、原文一致性、扩展存储键和 AI 外发／CSP 等已知风险；新工作流不是放弃原有准确性要求。这次文档更新不修改程序、配置、权限，也不启动真实投递。

## 已确认的开发约束：流程与状态不放在聊天里（2026-10-26）

1. **固定执行图**：主流程由程序状态机／迁移表控制，不以长 Prompt、聊天记忆、RAG 检索或模型自行规划代替。模型只处理当前节点的结构化输入；程序检查权限、证据和状态，决定是否进入下一步。版本化流程改变需明确升级，不让在途任务静默切到新流程。
2. **私有结构化资料**：本人资料、父母／家庭、教育、实习、项目正文和职责、附件版本分别建模，保留来源、确认版本和作用范围。精确字段查询优先，无须引入向量库；后端能直接查填的值不必经过模型。家庭敏感字段按当前表单和本人授权读取，不向所有角色开放整份档案。
3. **发布隔离**：正式数据在本项目 `private/`，代码库只含 schema 和虚构示例；暂存及打包检查防止数据、导出、快照、日志和凭据进入 Git／GitHub／静态站点。现有忽略规则不是充分保障，不读取真实资料测试防泄露。云模型外发权限与 Git 发布权限分开。
4. **结果台账**：公司／岗位精确索引保存提交与核验来源，页面状态确定性生成“已投递：岗位名”“未投递：没有符合职位”等文案。本人报告已投与官网核验分开；前者也禁止自动重投。名单去重不代替申请级去重。
5. **顺序调度**：队列持久化入队序号、活动公司、岗位顺序、运行锁及推进事件。本人启动后，当前公司所选岗位全部真实处理完或可靠确认无合适岗位时，自动开始下一公司。完成条件、暂挂、失败、本人报告与重复事件的规则见 WORKFLOW.md 第 9 节。
6. **少读而不失真**：任务开始时读取当前状态和所需资料版本；运行中缓存，在版本变化、恢复或官网规则需更新时重新查询。恢复依赖文件和现场，不依赖完整聊天；不能为了减少上下文读取而省略关键资格／额度／保存核验。

建议的纯程序边界为流程迁移、队列调度、资料查询、投递结果归并和问题队列；这些是职责划分，不要求一次搭框架或新增依赖。对应实现与最少验收步骤在项目私有计划中审核，不把本节设计当已运行能力。
